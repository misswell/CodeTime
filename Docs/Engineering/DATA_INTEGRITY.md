# 数据完整性设计

## 1. 完整性层级

CodeTime 的数据完整性由四层共同保证：

1. **Kopia 本地仓库**：内容寻址、加密、校验与快照。
2. **云端对象**：SHA-256 内容寻址，不可覆盖，写入后重新计算哈希。
3. **Generation 清单**：加密 `.ctm` 文件，记录文件列表、对象集合、字节数与快照 ID，是云端发布的提交点。
4. **任务与恢复日志**：SQLite 中的 GC/恢复/迁移状态，保证崩溃后可继续且不会重复破坏。

## 2. 对象写入与校验

### 2.1 哈希稳定性

`hashStable(url:initial:relativePath:)` 在哈希前后比较文件指纹（inode、大小、mtime）。若文件在哈希期间变化：

- 第一次变化：重新哈希并再次比较；
- 第二次仍变化：抛出 `objectCorrupt`。

哈希实现按块流式读取，不把整个仓库或大文件载入内存（CT-038）。

### 2.2 写入流程

```text
scan → hashStable → storeObject
                    ├─ 目标已存在：重新哈希
                    │    ├─ 一致：复用
                    │    ├─ 不一致：隔离 + objectQuarantined
                    │    └─ 无法校验：隔离 + objectCorrupt
                    └─ 目标不存在：复制到 .tmp → 哈希 → 指纹复核 → 原子移动
```

- 临时文件名带 `.tmp-` 前缀，GC 只会在宽限期后清理。
- 复制后再次校验源文件指纹，防止“复制期间源文件变化”。
- 已存在对象永不覆盖；异常对象移入隔离目录，数据保留且错误显式。

### 2.3 隔离策略

- 隔离目录位于对象根目录之外，不参与正常枚举。
- 同一对象再次写入时若哈希不匹配，仍先隔离再报错，不静默覆盖。
- 隔离不会删除用户数据；需要人工确认后清理。

## 3. Manifest 发布协议

```text
1. 扫描仓库，得到文件列表、对象集合与统计
2. 并发上传所有对象（有界并发）
3. 校验每个对象 SHA-256
4. 构造 manifest，validate(manifest:) 检查：
   - 格式版本、算法
   - 文件数、唯一对象数
   - 非空清单、相对路径合法、无重复路径
5. 加密 manifest → 写入 .tmp → 原子移动到 commits/<generation>.ctm
6. 等待 iCloud 上传确认
7. 回读并解密 manifest，比对 generationId 与对象集合
8. 写 recovery-info.json 与对象索引
```

规则：

- **提交点唯一**：第 5 步之前任何失败都不会产生可见 Generation。
- **回读失败即失败**：第 7 步不一致会移除已写入清单；若移除也失败，抛出“发布失败且无法移除未验证清单”，不留下虚假版本。
- **旧版本不受影响**：发布失败只清理本次临时文件与未验证清单。
- **上传确认不可跳过**：未确认上传不得进入第 8 步（CT-005、CT-006）。

## 4. GC 安全不变量

GC 分为 `enumerating → marking → tombstoning → gracePeriod → revalidating → sweepingObjects → completed`，任一阶段失败写 `aborted`。

执行前必须满足：

1. **完整枚举**：所有 `commits/*.ctm` 都能识别并解密；任一不可读立即中止。
2. **保留集合**：至少 `max(2, minimumGenerations)` 个最新版本，加上保留期内的版本。
3. **引用保护**：保留版本引用的对象全部存在；墓碑清单引用的对象也纳入保护集；墓碑不可读时中止。
4. **独立宽限期**：清单删除与对象删除等待 `sweepGrace`，与用户保留天数无关。
5. **重新验证**：宽限期结束后从当前清单重新构建有效对象集合；重新验证失败时恢复墓碑并中止。
6. **持久化**：每个阶段、每次对象删除都写入 GC 日志；日志读写失败视为错误，不继续删除。

因此，“删除对象”只在以下条件同时成立时发生：

- 对象不被任何当前可读清单引用；
- 对象不被任何墓碑清单引用；
- 对象年龄超过同步宽限期；
- 删除时清单集合已重新验证；
- 删除记录已成功写入日志。

## 5. 上传状态与 iCloud

`UbiquitousUploadTracker.waitForUpload` 明确区分：

| 状态 | 处理 |
|---|---|
| 文件已上传且无未推送变更 | 成功 |
| 尚未上传 / 正在上传 | 在超时内轮询 |
| 元数据不可读 | `metadataUnavailable` |
| 文件不存在且不是 iCloud 项 | `notICloudItem` / `metadataUnavailable` |
| 文件存在但不在 iCloud 容器 | `notICloudItem` |
| 协调失败 | `coordinationFailed` |

任何无法确认的状态都不会被当作“已上传”，因此不会产生虚假 Generation。

## 6. 验证语义

- **云端校验**：逐对象读取并计算 SHA-256，与清单比较；缺失对象报 `objectMissing`，内容不符报 `objectCorrupt`。
- **Kopia 校验**：读取退出码、错误计数与结构信息；非零错误不得标记 `verified`。
- **恢复后校验**：恢复报告同时要求仓库检查与快照检查通过，缺一不可（CT-018）。
- **维护任务**：只有实际执行且成功的结果才写入验证记录；失败保留错误，不覆盖为成功。

## 7. 错误分类与恢复

`CodeTimeError`/`CloudStoreError` 将错误分为永久错误与可重试错误：

- 永久错误：路径非法、格式不支持、密钥不匹配、仓库损坏、状态禁止。
- 可重试错误：临时 I/O、iCloud 同步、租约占用、进程超时。

重试使用 `RetryPolicy.default`：60/300/900/1800/3600 秒并带抖动；永久错误不进入重试队列。任务状态与 `next_retry_at` 持久化，Agent 崩溃后由租约过期回收。

## 8. 已覆盖的故障场景

| 场景 | 结果 | 测试 |
|---|---|---|
| 清单不可读 | GC 中止 | CT-001 |
| GC 中断 | 阶段恢复 | CT-002 |
| 对象同大小不同内容 | 校验失败 | CT-004 |
| 上传未确认 | 无 Generation | CT-005、CT-006 |
| 并发写同一对象 | 保留一份验证副本 | CT-008 |
| 发布中途失败 | 旧版本完整 | CT-009 |
| 哈希缓存过期 | 重算 | CT-010 |
| 恢复中断/复制失败/哈希不符 | 可恢复或安全失败 | CT-013、CT-014、CT-015 |
| 旧任务回调 | 不覆盖新状态 | CT-021、CT-022 |
| PID 复用 | 不误判存活 | CT-028 |
| 仓库丢失 | 不自动创建 | CT-035 |
| 磁盘满 | 显式磁盘错误（未本机注入） | CT-044 |
